# 0006. 생성 상태는 뷰가 아니라 문서에 둔다

- 상태: accepted
- 날짜: 2026-07-28

## 맥락

해석 생성 상태를 `InterpretationPanel` 안의 `@State`에 두었더니 세 가지 문제가 한꺼번에 나왔습니다.

첫째, ⌘N을 누르면 해석이 처음부터 다시 생성되었습니다. SwiftUI `WindowGroup`의 기본 ⌘N은 새 창을 여는 명령입니다. 새 창이 열리면 새 뷰가 만들어지고, 뷰에 붙어 있던 생성 상태가 초기화됩니다.

둘째, 인물을 바꿨다가 돌아오면 이미 만든 문장이 사라졌습니다. 계산은 밀리초지만 생성은 수십 초입니다.

셋째, 중단과 재개를 붙일 자리가 없었습니다. "이어서 하기"가 성립하려면 어디까지 만들었는지가 어딘가에 남아 있어야 합니다.

## 결정

`InterpretationStore`를 `@Observable`로 만들어 앱 수명 동안 유지합니다. 키는 인물 ID, 명식 서명, 엔진 식별자의 조합입니다.

```
Key(subject: 인물ID, signature: 명식서명, engine: "gemma-4-e2b" | "template")
```

명식 서명에는 사주 여덟 글자뿐 아니라 적용된 보정값도 들어갑니다. 유파 옵션을 바꾸면 서명이 달라지므로 자동으로 새 문서가 됩니다.

문서는 섹션 단위로 완료를 기록합니다. 재개는 "미완료 섹션부터"라는 명확한 의미를 갖습니다. 중간에 끊긴 섹션은 부분 문장을 버리고 다시 만듭니다. 문장 중간에서 이어붙이면 앞뒤가 어긋난 글이 나옵니다.

`Interpreter` 프로토콜은 전체 문서가 아니라 섹션 부분집합을 받습니다. 그래야 재개가 가능합니다.

창은 `WindowGroup` 대신 `Window`로 바꾸고 `CommandGroup(replacing: .newItem)`으로 ⌘N을 대체합니다. 명식은 문서가 아니라 사람이고, 사람은 사이드바로 고릅니다.

## 결과

- 사용자가 시키지 않으면 재생성하지 않습니다. `ensure()`는 캐시가 있으면 아무 일도 하지 않고, 중단 상태도 사용자의 의사로 존중합니다.
- 중단·재개·재생성이 각각 다른 동작으로 성립합니다.
- 오늘 화면과 캘린더도 같은 저장소를 씁니다. 날짜별 키를 쓰므로 어제 본 풀이가 그대로 남습니다.
- 실행 중 판정을 phase가 아니라 task 유무로 해야 합니다. phase는 첫 청크가 도착해야 `.running`이 되므로, 그 사이에 뷰가 다시 나타나면 같은 섹션에 두 번 이어붙습니다. 실제로 이 버그가 스크린샷 생성 중에 잡혔습니다.
