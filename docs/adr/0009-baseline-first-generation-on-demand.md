# 0009. 기준선을 항상 두고, 생성은 주문으로만 한다

- 상태: accepted
- 날짜: 2026-07-28
- 관련: [0002](./0002-separate-deterministic-engine-from-llm.md), [0006](./0006-generation-state-belongs-to-the-document.md)

## 맥락

0006에서 생성 상태를 뷰에서 꺼내 `InterpretationStore`로 옮겼습니다. 그 결정은 옳았지만, 키를 이렇게 잡은 것이 새로운 결함을 만들었습니다.

```
Key(subject: 인물ID, signature: 명식서명, engine: "gemma-4-e2b" | "template")
```

**엔진이 키에 있으면 모델을 켜는 것이 캐시 전체를 무효화하는 것과 같은 뜻이 됩니다.**

사용자가 실제로 겪은 순서입니다.

1. 앱을 다시 켭니다. 선택한 모델 ID는 UserDefaults에서 복원되지만 모델은 메모리에 없습니다. `isReady == false`이므로 키의 엔진이 `"template"`이 됩니다.
2. 설정에서 "사용"을 누릅니다. `container`가 생기고 `isReady == true`가 되면서 **키의 엔진이 모델 ID로 바뀝니다.**
3. `onChange(of: key)`가 발화합니다. 새 키에는 문서가 없으므로 `ensure()`가 성실하게 전량 생성합니다.

사용자는 문장을 갈아치우라고 지시한 적이 없습니다. 시스템은 빈 캐시를 발견하고 채운 것입니다. "모델을 고르면 갑자기 생성이 시작된다"와 "껐다 켜면 이미 본 문장을 다시 만든다"는 별개의 버그가 아니라 한 문장의 두 결과였습니다.

여기에 두 가지가 겹쳐 있었습니다.

- `ensure()`가 비용이 비대칭인 두 연산을 같은 함수로 다루었습니다. "없으면 채운다"는 밀리초짜리 규칙 엔진에는 옳지만 수십 초에 배터리를 쓰는 생성에는 틀린 정책입니다.
- 문서가 프로세스 안에만 살았습니다. 그래서 3번에서 예전 문장이 복원되지 않은 것이 아니라 **처음부터 없었습니다.** 종료가 곧 강제 전량 재생성이었습니다.

## 결정

### 1. 두 층을 분리한다

| | 기준선 | AI 문장 |
|---|---|---|
| 정체 | 계산 결과의 일부 | 사용자가 주문한 산출물 |
| 비용 | 밀리초, 결정론적 | 수십 초, 배터리, 비결정적 |
| 위치 | `InterpretationSection.baselineText` | `InterpretationStore` |
| 존재 | 항상 | 사용자가 만들었을 때만 |
| 잃으면 | 다시 계산하면 됨 | 사용자가 화남 |

`TemplateInterpreter`를 삭제했습니다. 규칙 엔진 문장은 해석기가 아니라 근거 원문을 이은 값입니다. 해석기 프로토콜에는 비용을 치르는 경로만 남습니다.

키에서 엔진이 빠집니다.

```
Key(subject: 인물ID, signature: 명식서명)
```

**모델을 켜는 것이 키를 흔들 방법이 이제 없습니다.** 정책이 아니라 구조가 자동 재생성을 막습니다.

어느 모델이 언제 썼는지는 키가 아니라 `Document.provenance`에 기록합니다. 모델별로 문장을 여러 벌 갖는 것은 사용자가 원한 적 없는 기능입니다.

### 2. 읽기는 앱이 알아서, 쓰기는 사용자만

`ensure()`를 삭제했습니다. 가드를 추가하는 것이 아니라 함수를 없앴습니다. 남은 진입점은 `generate()`·`resume()`·`stop()`·`discardDocument()`이고, 전부 버튼에서만 불립니다.

`onAppear`와 `onChange`는 `restore()`만 부릅니다. 디스크에서 읽어 오는 일이고, 없으면 아무 일도 하지 않습니다.

### 3. 모델 상태를 세 층으로 말한다

| 층 | 뜻 | 수명 |
|---|---|---|
| 설치됨 | 파일이 이 Mac에 있다 | 영구 |
| 쓰기로 함 | 사용자가 이 모델을 골랐다 | 영구 |
| 적재됨 | 지금 메모리에 있다 | 세션 |

UI가 "AI를 제시해도 되는가"를 판단할 때 보는 것은 앞의 두 층입니다(`isAvailable`). 적재는 생성 버튼의 첫 단계이며(`prepare()`), 화면에는 "모델을 불러오는 중"으로 나타납니다.

실행할 때 미리 올려두지 않습니다. 오늘 AI를 쓰지 않을 사용자에게 3.6GB를 물릴 이유가 없습니다.

`unload()`는 메모리만 비우고 선택은 남깁니다. 예전에는 여기서 선택까지 지웠고, 그래서 잠깐 메모리를 비운 사용자가 설정을 처음부터 다시 하게 됐습니다.

### 4. 비싼 산출물은 프로세스 밖에 둔다

Application Support에 JSON으로 보관합니다. 섹션이 완료될 때마다 씁니다 — 그 지점에서 앱이 죽어도 완성된 섹션은 남고, 다음 실행은 남은 것부터 이어갑니다.

파일명은 키의 SHA-256입니다. `hashValue`를 쓰면 안 됩니다. Swift의 Hasher는 프로세스마다 시드가 달라서 다음 실행에서 같은 키가 다른 파일명이 되고, 그것은 이 ADR이 고치려는 증상을 정확히 재현합니다.

보존 정책은 다릅니다. 명식 해석은 평생 한 벌이므로 영구 보관하고, 날짜별 풀이는 120일이 지나면 정리합니다.

`provenance.ruleSetVersion`이 현재 `rules.json`의 판과 다르면 화면에 표시합니다. 조용히 지우지 않습니다 — 이미 읽은 문장이 이유 없이 달라지는 것이 더 나쁩니다.

### 5. 라벨은 예측이 아니라 기록에서 나온다

예전 `engineName`은 "현재 설정으로 무엇이 나올지"를 말했습니다. 그래서 설정을 바꾸는 순간 이미 화면에 있는 문장의 출처 표기가 거짓이 됐습니다. 이제 `Document.provenance`를 읽어 "Gemma 4 · 7월 28일 오후 3:12에 씀"으로 표시합니다.

### 6. 검사로 박는다

`scripts/check_generation_policy.sh`가 네 가지를 검사하고 CI가 실행합니다.

- 뷰 생명주기 훅(`onAppear`·`onChange`·`task`) 안에서 생성을 시작하지 않는지
- `ensure` 형태의 "없으면 채운다" API가 되살아나지 않았는지
- `Key`에 엔진 정보가 다시 들어가지 않았는지
- Gemma 외의 `Interpreter` 구현이 생기지 않았는지

## 결과

- 모델을 고르는 것과 문장을 주문하는 것이 완전히 다른 행위가 됩니다.
- 앱을 껐다 켜도 만든 문장이 그대로 있습니다. 모델 선택도 그대로입니다. 설정 화면에 다시 갈 이유가 없습니다.
- 첫 실행 사용자가 보는 화면이 완결돼 있습니다. 모델 없이도, 다운로드 전에도, 생성 실패 후에도 근거 원문 해설이 그 자리에 있습니다.
- 스크린샷 생성기에서 해석을 미리 채우는 코드가 사라졌습니다. 스크린샷이 첫 실행 사용자가 실제로 보는 화면과 같아졌습니다.
- 대가: 사용자가 버튼을 누르지 않으면 AI 문장을 영원히 보지 못합니다. 그래도 근거 원문 해설이 완전하므로 잃는 것은 "매끄러움"뿐이고, 얻는 것은 "앱이 내 배터리로 내가 시키지 않은 일을 하지 않는다"는 신뢰입니다.
